# 扩大 Chrome 应用商店排名采集范围方案

日期：2026-09-30

> 状态更新（2026-10-01）：后续抓包已证明纯 HTTP Top 50 可行。本文保留为早期方案研究记录，当前结论以 [纯 HTTP Top 50 研究报告](纯HTTP-Top50研究报告.md) 为准。

## 研究结论

Chrome 应用商店搜索页的首个 HTTP 响应只包含前 10 条结果，但浏览器页面提供“Load more / 加载更多”按钮。实测每点击一次会追加 10 条结果，而且新增结果继续携带显式、连续的 `jslog index`。

本次对 `page editor` / `en` 的实测结果：

| 状态 | 结果卡片数 | 索引范围 | 索引是否连续 | 是否仍有加载更多 |
| --- | ---: | --- | --- | --- |
| 初始页面 | 10 | `0…9` | 是 | 是 |
| 点击 1 次 | 20 | `0…19` | 是 | 是 |
| 点击 2 次 | 30 | `0…29` | 是 | 是 |
| 点击 3 次 | 40 | `0…39` | 是 | 是 |

因此，现有的结果卡片校验逻辑可以继续用于第 11 名以后；限制来自“如何请求后续批次”，而不是排序数据本身。

## 官方 API 能否直接解决

不能。Chrome 官方公开的 Chrome Web Store API 面向开发者上传、发布和查询自己产品的状态，没有公开的商店搜索排名或搜索分页接口：

- [Chrome Web Store API v2](https://developer.chrome.com/docs/webstore/api/reference/rest)
- [Chrome Web Store API 使用指南](https://developer.chrome.com/docs/webstore/using-api)

所以扩大排名采集必须基于商店网页，而不能依赖官方搜索 API。

## 可选方案

### 方案 A：浏览器自动点击“加载更多”（已实现为验证 adapter）

使用 Playwright 驱动干净的 Chromium 会话：

1. 打开指定关键词和语言地区的搜索页；
2. 读取当前所有 `[data-item-id]` 结果卡片；
3. 校验扩展 ID、详情链接和 `jslog index`；
4. 如果结果数少于目标 `topN`，点击“Load more”；
5. 等待结果卡片数量增加，而不是使用固定睡眠；
6. 每一批加载后重新校验索引必须唯一且从 0 连续；
7. 达到 `topN`、目标扩展已找到、按钮消失或达到安全上限时停止。

优点：

- 与真实用户页面行为一致；
- 不需要复刻 Google 私有请求格式；
- 页面内部请求发生变化时，只要按钮和结果卡片仍存在，代码通常仍能工作；
- 可以同时保存截图、最终 DOM 和浏览器对照证据。

缺点：

- 比纯 HTTP 请求慢、占用资源更多；
- 需要安装浏览器自动化依赖和 Chromium；
- 必须明确控制登录状态、Cookie、代理、语言和地区，否则排序可能带有个性化因素。

### 方案 B：复刻页面内部的分页 RPC（已实现为默认生产 adapter）

“加载更多”由 Chrome 应用商店前端发起内部分页请求。理论上可以从页面初始化数据中提取续页令牌，再调用内部 RPC 获取后续批次。

优点：

- 速度快，资源占用接近当前纯 HTTP 方案；
- 适合大量关键词和频繁定时采集。

缺点：

- 不是公开 API，没有兼容性保证；
- 请求通常依赖 RPC 标识、页面构建版本、令牌和编码后的参数；
- 前端更新后更容易整体失效；
- 需要持续保存原始响应和完整诊断信息，避免静默产生错误排名。

该方案现已通过英文和 `zh_CN` 两组 Browser ground truth 严格验证，默认用于生产采集；浏览器模式继续用于定期验证和人工 fallback。

### 方案 C：只扩大关键词、不扩大单关键词深度

继续使用当前纯 HTTP 首屏采集，每个关键词只看前 10。该方案可以增加覆盖面，但不能回答“目标扩展实际排在第 10 名以后多少名”，因此不满足本次目标。

## 推荐架构

最初建议采用两级采集；当前实现已经升级为：

1. **默认纯 HTTP 模式**：首次 GET 处理 Top 10，再用 continuation token 获取后续批次。
2. **浏览器验证模式**：通过 `--adapter browser` 显式运行，用作 ground truth 和 fallback。

这样可以保留当前工具速度快、证据清楚的优点，同时把较重的浏览器成本集中到真正需要深挖的查询上。

建议新增命令：

```bash
npm run deep -- --keyword "page editor" --locale en --top-n 50
```

建议支持以下参数：

| 参数 | 作用 | 建议默认值 |
| --- | --- | ---: |
| `--top-n` | 最多采集多少名 | `50` |
| `--batch-delay-ms` | 每次加载更多后的最小间隔 | `1500` |
| `--max-loads` | 最多点击加载更多次数 | `9` |
| `--headless` | 是否无界面运行 | `true` |
| `--stop-on-found` | 找到目标扩展后立即停止 | `true` |
| `--save-screenshot` | 是否保存最终页面截图 | `true` |

## 结果语义需要调整

当前的 `NR` 容易被理解成“完全没有排名”，但现在它实际只表示“目标扩展不在已解析的前 10 条结果中”。扩大采集后建议改成明确状态：

- `rank: 23`：目标扩展在第 23 名；
- `notFoundWithin: 50`：已可靠检查前 50，但没有找到；
- `endOfResults: true`：已经到达结果末尾，仍未找到；
- `unknown`：页面或排序校验失败，不能下结论。

同时保存：

- `requestedTopN`：请求采集深度；
- `collectedCount`：实际采集条数；
- `loadedBatches`：加载的批次数；
- `collectionMode`：`http-first-page` 或 `browser-load-more`；
- `complete`：是否达到目标深度或确认到达结果末尾；
- 每批加载后的连续索引校验结果。

## 可靠性和限流策略

- 使用全新、未登录的浏览器上下文，避免账号历史影响结果。
- 固定语言参数、时区、User-Agent 和视口，并记录出口网络信息但不保存敏感标识。
- 不并行点击分页；同一查询严格串行加载。
- 等待 DOM 条目数增长，不依赖固定时间猜测页面是否加载完成。
- 单个查询默认最多采集 50 条；需要更深时显式提高上限。
- 关键词之间继续保留 5–10 秒间隔，并在 429、验证码或异常页面出现时立即停止。
- 每个批次都重新验证索引连续性；任意批次失败，整次排名标记为 `unknown`。
- 保存最终 HTML/DOM、结构化 JSON 和截图，以便页面结构变化时复盘。

## 建议实施顺序

1. 增加 Playwright 和新的 `deep` 命令，先支持 Top 50。
2. 为 10、20、30、50 条结果编写解析与连续索引测试。
3. 对 `en`、`zh_CN` 各运行一次 Top 50，并与浏览器页面人工抽查。
4. 做三次 Top 50 重复性实验，确认深层结果是否比首屏更易波动。
5. 稳定后再研究内部 RPC，把它作为可选的高速模式，而不是唯一模式。

## 实施状态

方案 A 已实现，Top 50 已成为 `probe`、`matrix` 和 `repeat` 的默认深度，可通过 `--top-n` 覆盖。

首次真实验证使用 `web page editor` / `en`：

- 成功加载 50 条结果；
- 点击“加载更多”4 次；
- 索引唯一且从 `0` 连续到 `49`；
- Edit Page 排名第 11；
- 旧版 Top 10 实验曾将它显示为 NR，扩大范围后得到了精确排名。

内部 RPC 高速模式已经实现为默认 adapter；Browser adapter 保留，没有删除。
